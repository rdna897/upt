# G2-S0 — Recovery ownership and completion fence (schema-10 design)

**Status:** Option B accepted as the G2 policy choice on 2026-10-16; this is documentation-only. S0b implementation, schema migration and deployment are **not** authorised by design approval. See [G2 policy](g2-mutation-completion-policy.md), [G2 issue #9](https://github.com/rdna897/upt/issues/9), [G3 issue #10](https://github.com/rdna897/upt/issues/10).
**Baseline:** public schema 9; merged PRs #13 (characterisation), #14 (R10), #16 (S0a SQLite primitives) and #19 (cleanup protection).
**Freeze:** No production deployment, service restart, schema migration or Docker/database mutation under this design PR.

## 1. Decision D10 — dedicated schema 10 selected as policy

| Candidate | Assessment |
| --- | --- |
| A — typed G2 evidence in `compose_bootstrap_fences` | **Rejected for G2:** namespace-consumer updates also insert a fence for the same logical key and operation ID, causing UNIQUE/PK collisions after image pull. Old R10 cleanup does not understand new image/backup claims. Mixed G2 and legacy evidence increases failure-domain coupling. |
| **B — `completion_fences` and `completion_fence_claims` in schema 10** | **Selected:** dedicated durable owner identity, typed indexed image/backup claims, separate namespace/bootstrap lifecycle, mechanical old-binary schema refusal. Requires separately approved offline 9→10 migration, no silent auto-migration, and a guarded release/downgrade plan. |
| C — `operation_runs.summary` only | **Rejected:** not reliably enforced by existing gates; new CLI `operation_runs` rows collide with web-only active and abandonment semantics. |

**Important:** Option B fixes the shared-table collision and adds a schema-level *binary compatibility check*; it does **not** itself solve own-operation admission, identity drift, truthful publication, operator release or retention. Those remain acceptance gates below.

## 2. Storage contract and offline migration

Approved conceptual storage shape (illustrative; exact DDL, compatibility and data-migration proofs require separate author review before coding):

- `completion_fences(operation_id TEXT PRIMARY KEY, logical_key TEXT NOT NULL, stack TEXT NOT NULL, compose_service TEXT NOT NULL, action TEXT CHECK(...), lifecycle TEXT CHECK(lifecycle IN ('active','manual','resolved')), evidence TEXT NOT NULL, created_at TEXT NOT NULL, updated_at TEXT NOT NULL)`. An unresolved partial UNIQUE index on `logical_key` permits one active/manual fence per *logical service*.
- `completion_fence_claims(operation_id TEXT NOT NULL REFERENCES completion_fences(operation_id) ON DELETE RESTRICT, kind TEXT CHECK(kind IN ('image','backup')), value TEXT NOT NULL, PRIMARY KEY(operation_id,kind,value))`. Index `(kind,value)` for many owners of a shared image or backup.
- `evidence` is bounded, versioned, strongly validated private data. The explicit table identity means malformed evidence cannot masquerade as a legacy bootstrap fingerprint. Unknown versions/invalid values fail closed for claims or admission until safely diagnosed.
- `operation_id` is a uuid4-hex completion ID for CLI; web uses its existing operation ID. **CLI does not create `operation_runs`.** The fence itself is the durable minimal intent. No FK from completion fences to web operation rows. Web records protocol capability on operation creation so absence of a later fence can be interpreted safely.

**Migration:** a schema-10-compatible binary must require an **offline, quiescent, explicit 9→10 transition** guarded by both UPT locks; preserve the immutable core-schema identity contract and create a verifiable backup/snapshot before changing schema. No implicit transition on startup, and no automatic reinterpretation of schema-9 evidence. Extend `state_transition` with explicit supported version gates and exact-idempotent migration tests. Existing schema-9 binaries already refuse version greater than 9 through `State._migrate`; test that their read and mutation entrypoints fail closed against schema 10.

**Rollback safety:** do **not** restore an old schema-9 snapshot over legitimate post-upgrade history. Binary downgrade requires *proof* there is no unresolved fence, no unreconciled protected evidence and no untranslatable post-upgrade state; otherwise refuse and use supported forward recovery. A state-preserving offline 10→9 transition, if feasible, needs its own separately approved design and tests. A binary revert alone is not enough.

## 3. Claims and identity: owner-scoped, multi-owner and fail-closed

Admission matches the exact proven `logical_key` **and** compatible stable (stack, Compose service) identity to prevent bypass by changed Compose file lists or moved directories. A conflicting same-service identity refuses admission pending reconciliation; unproven service identity refuses rather than defaulting to an unprotected path. Compare original/current Compose and container identities when necessary, but **image-sharing alone never blocks unrelated services' mutations**. Image claims only prevent destructive image deletion.

Claim table by mutation path:

| Path | Old/current image claims | Other image claims | Backup claims and proof |
| --- | --- | --- | --- |
| Ordinary / pinned update | The original running image | Any independent unresolved owner's earlier image remains protected by its separate claim/ref | Newly verified `backup_files` directory; source prestate identity/digests; immutable target observation bound once known |
| CLI rollback | Currently running image | Selected rollback target image | Existing target source backup **and a new pre-rollback backup** of currently active sources (added before this path is activated) |
| Web rollback | Currently running image | Selected rollback target image | Selected History source backup and captured pre-rollback recovery backup |
| Compose Apply / namespace | Existing dedicated fences and receipts remain authoritative | Do not silently merge their lifecycle into G2 | Existing recovery-bundle guarantees must not regress |

Do not put target image IDs in the *initial* guard when a mutable tag is not yet resolved: require a versioned, bounded evidence-enrichment write under the active fence after target observation, before any subsequent effect needing that identity. The guard must remain effective if enrichment fails; release cannot rely on unsupported pre-knowledge. Capture source prestate hashes and verified before/after evidence as required for each possible operator resolution. Never store secret Compose contents, authentication or environment values.

**Independent ownership:** G2 claims never `REPLACE` or delete a `protected_images` row. `State.record` must not overwrite an existing `NULL history_id` manual/namespace protection. It can preserve that row and create the new `rollback_refs` entry in the same transaction. Any other existing protection ownership remains intact unless an explicitly approved migration proves safe resolution. Record whether any optional legacy `INSERT OR IGNORE` belt inserted a row; it is not the authority for G2 cleanup and must not be treated as a sole owner.

## 4. Lifecycle, correctness and self-exemption

1. **Prepare** under `update.lock`: validate logical and stable service identities; perform preflight and capture source backup(s). Dry-run writes no guard. Store web capability independently at `create_operation`.
2. **Arm** in a short `State.connect` transaction immediately **before the first actual side effect**, after final ordinary preflight checks. Insert one `active` fence with exact claims; if an attempted commit is ambiguous, prohibit mutation until a successful read proves the exact fence and claim rows committed. No Docker, network, filesystem mutations or sleep inside SQLite.
3. **Namespace exception:** existing namespace-consumer updates already use their *own* `mark_namespace_update` fence. Explicitly **exclude** them from G2 fence arming unless a later separately approved integration replaces their transaction protocol. Preserve namespace code paths and audit their earlier pull/tag exposure as a distinct pre-existing issue.
4. **In-flight checks:** a guarded web worker may bypass **exactly its own G2 fence** for internal repeated `pre_recreate_check` / `_verify_compose_runtime_identity` validation. Accept the owner ID only from trusted core/agent context, verify fence type, logical key, service identity and active lifecycle. Never accept an arbitrary browser-supplied owner ID. Other fences and pre-existing namespace/bootstrap fences still refuse. Front-door admission never exempts a candidate owner by default.
5. **Finish atomically:** `State.record` must publish truthful matching History, all `rollback_refs`, non-destructive image protection and `UPDATE completion_fences SET lifecycle='resolved' WHERE operation_id=? AND logical_key=? AND lifecycle='active'` in **one transaction**. Require exactly one fence row changed or roll the entire transaction back. On ambiguity, reconcile matching History and fence state using P5; do not insert duplicate or falsely report workload failure.
6. **Blocked/recovered/uncertain:** if armed then refused before mutation, resolve only when pre-effect/no-side-effect conditions are verified. For genuine failure, resolve atomically with an accurate History record **only after trustworthy recovery/no-effect proof**; otherwise retain as `manual` or `active`. A failed `active→manual` write is safe because an active fence is still enforced. No automatic Docker compensation solely for persistence failure.
7. **Interruption:** CLI crash leaves fence durable, without a web active slot. Web interrupted outcomes must be reconciled as part of the S1 web rollout, not delayed to S4. A new-protocol web row lacking a committed fence proves mutation was *not authorised*; existing legacy web rows retain prior recovery semantics. Resolved fences must remain queryable long enough for uncommitted web terminal status to be reconstructed; their retention is not keyed solely to active claim eligibility.

## 5. Enforcement and safe operator recovery

- **Service mutation:** extend the `assert_service_unfenced` family of checks to all relevant paths, including `restart`, `remove`, `convert`, `restore-compose`, Compose plans/bootstrap, namespace operations, relevant internal direct mutations, and web/CLI admission. A malformed/unreadable fence cannot grant mutation authority. If the service key changes, refuse via the stable identity cross-check.
- **Image deletion:** `retention._removal_blocker` or equivalent shared State predicate is used by retention (including forced overrides), `upt cleanup`, and `remove --images`, both during eligibility and immediately before removal. Any unresolved image claim blocks deletion, independently of unrelated owners. Keep all R10 resolved/unresolved `protected_images` and `rollback_refs` checks.
- **Backup deletion:** validate claimed paths strictly under managed roots, reject symlinks/escaping paths, protect *all* claimed backups past age cutoff, recheck under the update lock before each filesystem delete, and preserve existing `compose-recoveries` retention semantics.
- **Other owners:** image-sharing does not block unrelated service admission. Existing NULL-history manual protections are not cleared or replaced. Multiple unresolved owners can claim the same image via separate indexed claim rows.
- **Privacy:** never expose fence evidence, image claims, full identities or filesystem paths through raw `operation_runs.summary`, `webservice.operation_status`, HTTP, SSE or web presentation. Only allowlisted operator-safe public status and a trusted administrator's local reconciliation report.
- **Release:** before *any* G2 fence writer is active, provide a **minimal, audited, operator-only, lock-held** reconcile/release path. It identifies exactly one fence and validates stable owner identity, current running image, claimed images, backups, source hashes and stored target observations. Publish a corrective History record with provenance only on independently proven postconditions; otherwise retain the fence and explain missing proof. No blind force-unlock, direct database edits or fabricated success. Whether an explicitly audited operator attestation may support release in genuinely unprovable cases remains an **owner decision**, not implicit authority.
- **Retention:** unresolved fences and claims are never automatically pruned. Resolved G2 fences may be aged/pruned only under **G2-type-scoped** predicates after web terminal/History reconstruction dependencies expire and all claims are resolved. Do not prune or reinterpret namespace/bootstrap fence rows. Set a finite reviewed metadata retention policy and test bounded lookup performance; if proof requires longer retention, explicitly preserve records.
- **Downgrade:** schema-9 binaries refuse schema 10 at the compatibility check, and offline transition/release tooling must verify no unresolved new evidence. Test an old-binary attempt and the rejection before any file/Docker mutation.

## 6. Test gates and implementation order

- **S0a — completed (merged PR #16):** before-/during-commit classification, per-call SQLite timeout and deterministic fault-injection harness. No workload or schema changes.
- **S0b — implementation PR open for final author review** ([record](g2-s0b-schema10-implementation.md)): explicitly approved offline schema 9→10 migration; two dedicated tables and indexes; guard admission/image/backup/downgrade predicates; privilege/redaction coverage; namespace/bootstrap regression tests. No active new G2 writers yet.
- **S0c — owner-scoped atomic publication and recovery:** shared `State.record` transaction composition, evidence enrichment, blocked/no-effect lifecycle, minimal audited release, and fault/rollback tests. Activate each fence writer **with** the corresponding fixed S1/S2/S3 completion error handler, not before.
- **S1:** ordinary CLI update fix and batch-retention guards; web update completion *and post-restart recovery* together (D9 required). **S2:** pinned update, including namespace exclusion. **S3:** CLI/web rollback, pre-rollback backup and identity guard. **S4:** Compose Apply integration and cross-path verification, separately authorised.

Mandatory synthetic tests: schema 9→10 offline transition and no silent startup migration, schema-9 binary refusal on schema 10, 10→9 rollback gate; namespace-consumer path unchanged; internal web own-fence revalidation; missing/conflicting logical-key service paths and stable identity drift; shared images independent owners; NULL manual protection byte-for-byte unchanged; ambiguous fence/History commits; atomic resolution rowcount failure; in-flight before/after evidence enrichment; guarded and ordinary backup TTL; forced retention, `remove --images`, `upt cleanup`; restart/convert/remove/restore-compose; batch CLI partial failures followed by automatic retention; CLI-only crash; HTTP/SSE privacy; malformed evidence; resolved fence pruning preserving namespace receipts.

**Approval gates:** D3, D3b, D3c, D8, D9 and D10 are accepted **policy choices**, not tested implementations. S0b requires a separately approved offline migration/storage/inert-enforcement PR and final author review. No fence writer activates until audited operator recovery and the matching corrected mutation path exist. D9's API/UI/SSE and restart compatibility must be tested before web activation. The deployment freeze remains in force.
